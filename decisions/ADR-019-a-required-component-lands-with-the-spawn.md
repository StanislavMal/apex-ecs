# ADR-019 — Обязательный компонент приходит вместе со спавном и вставкой, а не после них

Статус: принято 2026-10-07
Смежно: движковые ADR-293 / TD-683 (производный `DrawnMesh` — найдено прибором), D2-4 (required components)

## Контекст

Требование `C → R` (D2-4) исполнялось замыканием из очереди хуков: спавн бандла без `R` строил архетип
бандла, клал туда строку, а затем замыкание делало `world.insert(e, R::default())` — переезд строки в
архетип с `R`. И так на каждое требование, транзитивно. Хуки при этом видели полный состав, но цена была
переездом архетипа на каждое требование каждой сущности.

Нашёл движок прибором (`diag_drawn_mesh_cost`, `apex-render/src/drawn_mesh.rs`, релиз, 100 000
стандартных рисовальщиков, медиана из пяти): одно новое требование (`MeshRenderer → DrawnMesh`) подняло
спавн с 10,26 до 20,89 мс — вдвое. Той же ценой платили и прежние требования (трансформы у
`MeshRenderer`, камер, ламп), когда бандл их не нёс.

Попутно: `require_component` руководство называло идемпотентным, а реестр на повторное объявление
добавлял второе замыкание, исполнявшееся на каждое появление `C`.

## Эталон

Bevy (пин `654bcde0e`) сворачивает требования в бандл: `BundleInfo` собирает требуемые компоненты и их
конструкторы при регистрации бандла (`crates/bevy_ecs/src/bundle/info.rs:126-153`), спавн кладёт их в
архетип бандла; вставка считает архетип «после» с добавленными требованиями
(`bundle/info.rs:509-554`, `required_components` в `insert.rs`).

## Решение

1. **Реестр хранит требования второй формой** — `(ComponentId R, запись значения по умолчанию)`
   (`ComponentRegistry::required_defaults`, `RequiredDefaultFn`: пишет `R::default()` в строку колонки,
   только данные). Объявление пары идемпотентно (повтор ничего не меняет); у реестра есть поколение
   требований (`requires_generation`).
2. **Бандл сворачивает требования** (`BundleInfo::required`): при разрешении типа бандла берётся
   транзитивное замыкание требований, которых бандл не несёт; архетип бандла строится с ними; кэш бандлов
   разрешается заново, когда поколение требований сдвинулось (требование, объявленное после первого
   спавна бандла, доходит до следующего).
3. **Все дороги спавна** пишут значения по умолчанию в ту же строку: `spawn`/`spawn_reserved`
   (`write_required_defaults` с тиками и длиной, как `write_into_batch`), `spawn_many` и пакетный спавн
   команд (`spawn_bundles_bulk`: только данные в цикле, тики и длина — по колонке после цикла, как у колонок
   бандла; так откат при панике, усекающий только `entities`, не оставляет колонку длиннее строк), копия
   лестницы атрибуции (`spawn_ladder.rs`).
4. **Вставка** (`insert`, `insert_raw`, пакетная `insert_parts` команд): целевой архетип — текущий + новый
   компонент + его недостающие требования транзитивно (`insert_target`), один `move_entity`, значения по
   умолчанию — в перемещённую строку (`write_inserted_requirements`). События `Added` требований ставятся в
   очередь явно — их `on_add` срабатывает, как срабатывал из отдельной вставки.
5. **Замыкания-вставки и очередь хуков для требований убраны.** Все шесть дорог, добавляющих компонент
   (`spawn`, `spawn_many`, пакетный спавн команд, `insert`, `insert_raw`, `insert_parts`), сворачивают требования
   сами; замыканию на очереди оставалось только убедиться, что требование на месте, — за цену события `Added` и
   `has_component` на каждое требование каждой сущности. `ADDED_NOTIFY_MASK` — только `FLAG_ON_ADD`; флаг
   требований больше не взводит `any_flags` (это не подписка).

## Свидетели

- `a_required_component_lands_with_the_spawn_not_after_it` — все три дороги спавна, транзитивность, явное
  значение побеждает, требование после кэша бандла, тик добавления спавна, требование с кучей (`String`),
  идемпотентность объявления. Свидетель «без переезда»: архетип голого бандла не строится. Инъекция «не
  сворачивать» — RED.
- `an_inserted_component_brings_its_requirements_in_the_same_move` — `insert` и `insert_parts` команд;
  свидетель «один переезд»: ни одна строка не жила в архетипе с владельцем без требования (цепочка рёбер
  может назвать такой архетип пустым — ёмкость его вектора сущностей нулевая); `on_add` требования
  срабатывает на вставке, на спавне и на командах. Инъекция «не сворачивать во вставке» — RED.
- Оба теста — под Miri (целевой прогон): без UB, утечек и двойного освобождения.

## Цена (движковый прибор `diag_drawn_mesh_cost`, релиз, 100 000, медиана из пяти)

| бандл стандартного рисовальщика (несёт трансформы) | до | после |
|---|---|---|
| требований нет | 10,26 | 10,37 |
| требуются трансформы (бандл их несёт) | — | 9,91 |
| требуются трансформы + `DrawnMesh` (бандл его не несёт) | 20,89 | **12,92** |

Требование, которого бандл не несёт, стоит теперь записи своей колонки (+3,0 мс на 100 000 — +30 нс на
сущность, цена любого компонента), а не переезда архетипа (+11 мс). Требование, которое бандл несёт, больше
не стоит диспетчера хуков: спавн с ним — 9,91 против 10,37 без него (шум одного порядка).

Бандлы без требований (бенч ядра `cargo bench -p apex-bench -- spawn`, «до» — worktree на `0d6a142`, подряд
на свободной машине): `spawn_wide` 615,9 → 619,6 мкс, `commands_spawn` 253,9 → 253,6 мкс — в шуме.

## Последствия

- Требование больше не стоит переезда архетипа ни на спавне, ни на вставке.
- **Порядок `on_add` между владельцем и требованием изменился.** Раньше `on_add` требования `R` срабатывал после
  `on_add` владельца `C`: `R` вставлялся из очереди хуков владельца, и его событие вставало в хвост. Теперь события
  `Added` спавна встают в очередь по возрастанию id компонентов, вставки — владелец, затем требования; `on_add`
  требования может сработать раньше владельца. Оба хука, как и прежде, видят полный состав — это и было
  контрактом D2-4; порядок между хуками разных компонентов контрактом не был, и ни один свидетель ядра и движка на
  него не опирался.
- Промежуточные архетипы цепочки рёбер вставки создаются пустыми (как и раньше у `insert_parts`) — память
  на описание архетипа, не на строки.
