# ADR-022 — Система без состояния — функция, а не unit-структура

Статус: принято 2026-10-16
Смежно: ADR-002 (остаток: «требует vis-поддержки в `system!`»), ADR-021, D2-1 (plain-fn системы)

## Контекст

Тот же полевой отчёт, что и в ADR-021 (боевой крейт, HEAD `213f303`). Ещё две проблемы, обе в
`system!`:

1. **Нет видимости.** `system! { fn name(…) { … } }` объявлял приватную unit-структуру `name`, а
   `system! { pub fn … }` не разбирался («no rules expected keyword `pub`»). Системы и регистрацию
   расписания приходилось держать в одном модуле. Внутри ядра это известно давно: ADR-002 откладывал
   перевод ручных `AutoSystem` на `system!` именно из-за этого.
2. **Имя системы захватывает привязки.** Unit-структура живёт и в пространстве образцов модуля.
   Рядом с системой `pilot` замыкание `|_, (mut body, ship, pilot)|` в любой другой системе модуля
   переставало компилироваться (E0530, E0308): идентификатор в образце разрешался в структуру. Так же
   ломается `let pilot = …`. Типичный случай — система названа как компонент или переменная.

Попутно: ветка `Cmd` писала `apex_core::Commands` вместо `$crate::Commands`, то есть ломалась у
крейта, подключившего ядро под другим именем.

Предложение из отчёта — генерировать структуру в CamelCase — в `macro_rules` невыполнимо: менять
регистр идентификатора он не умеет. Подменить структуру на `const` или `static` тоже не выход: они
перехватывают имена в образцах так же (E0530). Не перехватывает только функция.

## Решение

1. **Форма без состояния объявляет функцию**, которая возвращает систему:
   `system! { fn integrate(…) { … } }` → `fn integrate() -> impl AutoSystem`, внутри неё — локальная
   структура нулевого размера `__ApexSystemFn` с тем же `impl AutoSystem`. Эксклюзивная форма
   (`world: &mut World`) так же даёт `fn name() -> impl ExclusiveSystem`. Регистрируемое имя
   (`AutoSystem::name` / `ExclusiveSystem::name`) — по-прежнему имя функции, поэтому `chain(&["…"])`,
   строковые `before`/`after` и отладочный план не меняются.
2. **`IntoAutoSystem<M>` / `IntoExclusiveSystem<M>`** (`apex-core`, `system_param.rs`) — «что
   называет систему»: сама система (структура, замыкание `FnMut(&mut World)`) или функция
   `Fn() -> S`. Маркер разводит две реализации, как у plain-fn систем. Через них идут все входы
   планировщика: `add_systems` (кортежи тоже), `sys("имя", …)`, `SystemConfig::exclusive`, тестовые
   `add_auto_system*` и типизированные цели `.before(x)`/`.after(x)`. Типизированной целью теперь
   может быть и эксклюзивная система (раньше её не было вовсе), под именем, которое регистрирует
   `SystemConfig::exclusive`.
3. **Видимость и атрибуты во всех шести ветках:** `$(#[$attr:meta])* $vis:vis` перед `fn` и
   `struct`. И то и другое переносится на итоговый элемент (функцию или структуру), так что работают
   doc-комментарии, `#[cfg]` и `pub(crate)`.
4. **`$crate::Commands`** в ветке `Cmd` (гигиена; см. «Гейт» о границе).

Места вызова не меняются: `add_systems(stage, (integrate, steer))`, `sys("x", integrate)`,
`.after(integrate)`. Ломается только код, который называл систему **типом** или звал её методы на
значении (`integrate.run(ctx)`, `<integrate as AutoSystem>::name()`). В ядре и движке таких мест нет:
движок собрался без единой правки, в ядре переименованы 12 систем примера `perf.rs`, которые
макрос примера объявлял в CamelCase (`SoloSys0` → `solo_sys_0`): как функции они давали
`non_snake_case`.

## Отвергнуто

- **Документировать ограничение и советовать plain-fn системы.** Обход рабочий, но `system!` —
  единственный путь к выводу доступа с разрезанием строк (ASD) и к своему диалекту параметров.
  Оставлять в нём ловушку, которую нельзя обойти внутри самого макроса, — полумера (§0.2b).
- **Процедурный макрос с CamelCase-структурой.** Структуре всё равно нужно значение для регистрации
  под именем функции, а значение, которое не перехватывает образцы, — это функция. Процедурный
  макрос пришёл бы к тому же устройству дороже.
- **Структура с подчёркиванием (`_pilot`) плюс константа.** Константа перехватывает образцы так же,
  как unit-структура.

## Последствия

- Цена в кадре нулевая. Функция возвращает ту же структуру нулевого размера с той же реализацией;
  признак `stateful` (`size_of > 0`) и разрезание строк не меняются.
- Публичная структура **с состоянием** может быть видна не шире своих компонентов: её `impl AutoSystem`
  называет их в `type Query` (E0446). Форма-функция их прячет за `impl AutoSystem`, поэтому
  `pub fn` годится и для приватных компонентов.
- Остаток ADR-002 (перевод ручных `AutoSystem` в `apex-input` на `system!`) больше не заблокирован
  видимостью.

## Гейт

`apex-scheduler/tests/unified_system.rs`:
- `pub_systems_from_another_module_register_and_order_from_here` — `pub fn`, `pub(crate) fn` с
  `&mut World` и `pub(crate) struct` объявлены в соседнем модуле, зарегистрированы и упорядочены
  типизированными целями (в том числе эксклюзивной) из этого модуля; строковый API видит то же имя;
- `a_renamed_registration_takes_the_function_form` — `sys("имя", функция)`;
- модуль `attributes_reach_the_system` — `#[cfg(any())]` над системами, ссылающимися на несуществующие
  типы: потерянный атрибут — ошибка сборки.

`apex-scheduler/tests/system_binding_names.rs` — замыкание и `let` с именем системы; цель проходит,
если компилируется. Это отдельная тест-цель: при ошибке разбора макроса (`pub`, атрибут) rustc не
доходит до разрешения имён, и в общем файле класс затенения не был бы виден сам по себе.

Инъекции 2026-10-16, каждая против своей тест-цели:

| Инъекция | Результат |
|---|---|
| макрос `213f303` целиком | `system_binding_names`: E0308/E0369/E0609 (имя разрешилось в структуру); `unified_system`: «no rules expected `pub`/`#`» |
| форма без состояния теряет `$vis` | E0603 `function public_inc is private` |
| форма без состояния теряет атрибуты | E0425 `ThereIsNoSuchComponent` |
| эксклюзивная форма теряет атрибуты | E0425 `ThereIsNoSuchType` |
| нет `OrderTarget` для эксклюзивной системы | E0277 на `.after(public_spawn)` |

`$crate::Commands` проверен стендом вне репозитория: крейт с зависимостью `ecs = { package =
"apex-core" }` и системой с `cmd: Cmd` компилируется, а с прежним `apex_core::Commands` даёт E0433.
Гейтом это не закреплено: переименование ядра целиком всё равно не поддерживается, потому что
`#[derive(Component)]` (процедурный макрос, `$crate` ему недоступен) пишет `apex_core::` жёстко.
Правка — гигиена `macro_rules`, а не новая возможность.
