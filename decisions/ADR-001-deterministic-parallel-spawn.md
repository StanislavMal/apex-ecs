# ADR-001 — Детерминированный параллельный спавн entity (D8b)

**Статус:** принят (кампания WAVE6B, 2026-07-04) · план-источник `plans/archive/WAVE6B_SOUNDNESS_DETERMINISM.md`

**Контекст.** `EntityReserver::reserve()` берёт id из ОБЩИХ атомиков (`lease.cursor.fetch_sub`,
`high_water.fetch_add`). При спавне из параллельных систем (через `Commands`) порядок атомарных
операций разных rayon-потоков → **недетерминированное** присвоение id run-to-run (как и в Bevy),
И это точка contention на общем атомике. Недетерминизм ломает record/replay, rollback-netcode и
детерминированные golden-тесты. `independent()` УЖЕ продаёт детерминизм порядка систем (§0.2a) —
недетерминированные id делали это обещание частично ложным.

Естественное противоречие: плоский `u32`-id, одновременно **eager** (известен в параллельной
фазе до flush, как `Commands::spawn().id()`) и **детерминированный** (= позиция в глобальной
последовательности), невозможен без знания числа спавнов систем меньшего ранга, которое в
параллельной фазе неизвестно. Развилка (A) remap-at-flush отвергнута: ломает семантику «id из
`.id()` можно сразу положить в ресурс» (провизорный ≠ финальный), регресс паритета с Bevy.

**Решение.** Схема (B) — **per-system детерминированные id-блоки, eager = final** (opt-in,
`Scheduler::set_deterministic_spawn(true)`, **дефолт OFF**):

- Планировщик знает детерминированный порядок систем стадии (ранг R; D8a дал tie-break). В начале
  стадии каждой command-системе выдаётся приватный блок с **rank-детерминированной базой**
  (`World::reserve_entity_block` на main-потоке в порядке ранга). Внутри блока система резервирует
  приватным счётчиком — eager, финальный, детерминированный, **без cross-thread contention**.
- Блоки **reuse-aware**: `reserve_block` сперва тянет освобождённые слоты из аренды free-list
  (descending, как `reserve_from`, один bulk `fetch_sub`), затем свежие из high-water; хвост
  незаспавненного блока возвращается в free-list БЕЗ gen-инкремента (`reclaim_block_tail`) → под
  despawn+respawn churn id-пространство **ограничено** (не растёт), а reuse детерминирован.
- Команды применяются в **rank-порядке** систем стадии (per-system буферы вместо
  `thread_commands[worker]`) во всех трёх ветках диспетча. Блоки сеются для ВСЕХ command-систем
  независимо от SEQ/PAR-пути → id **path-independent** (timing не влияет).
- Размер блока адаптивен (наблюдённый peak × 2, `system_spawn_history`) → steady-state без overflow.

**Последствия.**
- ✅ **Гарантия (§0.2a — продаём ровно то, что держим): single-binary детерминизм, ВКЛЮЧАЯ churn.**
  Один бинарь при одинаковом стартовом snapshot + входах воспроизводит идентичное присвоение id,
  порядок применения команд, iteration-independent результат. Достаточно для record/replay и
  rollback на одной машине/бинаре. **Безусловна в steady-state** (после адаптивного прогрева).
- ❌ **Вне scope:** битовая FP-идентичность и кросс-платформенный/кросс-компиляторный детерминизм
  (отдельная ось: fma/денормали/fast-math). НЕ заявляем.
- **§0.9 превосходство:** приватный per-system счётчик убирает contention → массовый параллельный
  спавн **20.5× быстрее** shared-atomic `reserve()` (спайк, 24k entity). Детерминизм и перф тянут
  в одну сторону. Bevy детерминизм id под параллелизмом НЕ гарантирует.
- **eager `.id()`** сохранён (base+counter, без remap). Паритет с Bevy (reserved = final).
- **Дефолт OFF** → путь `reserve()` неизменен, goldens движка byte-identical (656/0), нулевой риск
  дефолту. Машинерия дормантна при OFF.
- **Узкий фронтир (остаток) — БОЛЬШЕЙ ЧАСТЬЮ ЗАКРЫТ (addendum 2026-07-06, кампания CORE_POLISH
  волна 1.1).** Было: при overflow блока в кадре-1/спайке система падала в общий (недетерминированный)
  путь ТОТ кадр, ТИХО. **Сделано — эскроу-margin:** каждый сеемый блок = адаптивный
  `block_size_for` (peak×2) ПЛЮС эскроу (половина блока, rank-детерминированный приватный хвост), т.е.
  `Scheduler::seed_size_for`. Спайк, превысивший адаптивный блок, теперь тянет ДЕТЕРМИНИРОВАННЫЕ id из
  эскроу вместо гонки на общем reserve'е → гарантия расширена с «steady-state» до «steady-state +
  спайки в пределах эскроу (~3× peak)». Неиспользованный эскроу-хвост реклеймится (id-пространство
  ограничено). **За пределами блок+эскроу** — фолбэк на общий путь КАК ПРЕЖДЕ, но теперь ГРОМКИЙ
  (§0.2a): `BlockCursor.overflowed`-флаг → `warn_once!` + счётчик `Scheduler::deterministic_overflow_
  count`. Тесты `escrow_keeps_spike_within_margin_deterministic` / `overflow_beyond_escrow_is_loud_
  and_still_correct` (`d8b_determinism.rs`), Miri чист. **Остаточный фронтир:** спайк за пределами
  блок+эскроу всё ещё недетерминирован тот кадр (но громкий + блок растёт) — принято: эскроу покрывает
  реалистичные спайки, а бесконечный детерминированный overflow не окупается (§0.2b).
- Граница гарантии видима пользователю: `Apex_ECS_Руководство_пользователя.md` §6.6a.
