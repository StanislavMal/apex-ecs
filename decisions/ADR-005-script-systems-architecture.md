# ADR-005 — Архитектура Lua-систем (скриптинг как первоклассные системы планировщика)

**Статус:** принят (кампания CORE_POLISH+SCRIPT_SYSTEMS, волна 3, 2026-07-07) · план-источник
`plans/archive/CORE_POLISH_SCRIPT_SYSTEMS.md` (§4 «⚙ ДИЗАЙН ФАЗЫ B», §5 «дизайн-нота»). Смежные:
ADR-001 (детерминизм спавнов D8b), ADR-002 (declared-access soundness, `_unchecked`/гейты), ADR-004
(Р-1 «доступ = параметры»).

**Контекст.** Контекст-решение волны 6 CORE_AUDIT (§10.8): скриптинг «обязан встать на общий,
валидируемый ядром механизм». `DynQuery`/`DynQueryMut` были сделаны и назвали скриптинг консумером, но
миграция не выполнена: `apex-scripting` шёл собственным unsafe-путём через `_meta`, а
`ScriptEngine::run(dt, &mut world)` был монолитом ВНЕ планировщика. Цель — Lua-логика как обычные
системы планировщика (конфликт-детекция, детерминизм, hot-reload), без воскрешения soundness-дыр,
закрытых волнами 6/6б (ADR-002).

**Развилка (внешнее предложение, 2026-07-06):** `ScriptEngine` как ресурс; каждая Lua-система —
Rust-система с типизированными `Query`-параметрами + `lua: Res<ScriptEngine>`; `ScriptContext`
`Rc<RefCell<>>` → `Arc<Mutex<>>`; mlua-фича `send`; ожидание — планировщик параллелит Lua-системы;
оценка ~100–200 строк.

**Принято из предложения (цель):** Lua-системы как первоклассные системы планировщика с декларациями
доступа.

## Решение

**Lua-системы — main-thread `NonSend`-вид систем планировщика; эксклюзивность VM выражена в
access-модели, не в блокировке.**

- **`NonSendSystem` (без `Send`/`Sync`)** + `SystemKind::NonSend { system, access }`. Access
  участвует в конфликт-детекции как у `Parallel`; исполнение пришпилено к main-потоку. Следствие:
  `Scheduler` становится `!Send` (хранит `!Send`-боксы) — проверено, ничто в проде не двигает
  Scheduler между потоками (драйвер play-режима живёт у хоста на своём потоке); `run()` не в
  `pool.install`. Future crash-isolation VM всё равно требует thread-affinity → `!Send` корректен.
- **Конкурентность.** NonSend бежит на main ВНУТРИ `rayon::in_place_scope` конкурентно с Send-воркерами
  стадии. Sound: `compile` развёл конфликтующие системы по стадиям → в одной стадии данные NonSend и
  воркеров дизъюнктны (тот же аргумент, что воркер↔воркер).
- **Токен `ScriptVm`** — ZST-маркер-ресурс; каждая Lua-система декларирует на него `write`. Планировщик
  честно **сериализует Lua↔Lua** (одна VM) и **параллелит Lua↔Rust** по реальным декларациям. Никакого
  `Mutex`. Конфликт-детекция сравнивает `TypeId`-векторы → `ComponentBinding` несёт `type_id`.
- **Динамические декларации.** `system{ name, query, fn }` из Lua → `registrar` транслирует `QueryDesc`
  в `AccessDescriptor` (component `TypeId` + write `ScriptVm`) и регистрирует раннер через нижний слой
  той же регистрации — `Scheduler::add_dynamic_nonsend_system(name, access, runner)` (типизированный
  `add_systems` — частный случай того же backbone).
- **Soundness записи (переоценка §0.2b, B3a).** Раннер получает `&World` (стадия держит `&World`),
  поэтому commit НЕ формирует `&mut World` (это было бы UB под Tree Borrows рядом с живыми SubWorld
  воркеров). Введён `#[doc(hidden)] unsafe QueryBuilderMut::from_declared_cell(&World)` /
  `World::query_builder_mut_declared` — write-запрос из `&World`, где эксклюзив декларированных колонок
  доказывает ПЛАНИРОВЩИК (декларации + сериализация конфликтов), а запись идёт только в
  interior-mutable колонки. Тот же путь звучен и для монолита (тривиальный эксклюзив). Enforcement:
  `query`/`commit` резолвят только декларированные компоненты (undeclared → `anomaly!`), что делает
  S7-гейт `DynItemMut::get_mut_ptr` содержательным.
- **Детерминизм и эффекты.** Все отложенные эффекты (spawn/despawn/resource/event) идут через
  per-system `Commands`-слот; спавны получают детерминированные id (ADR-001/D8b —
  `access.uses_commands` сеет rank-блок под `set_deterministic_spawn`). Ресурсы/события — через
  `commands.add(Send-closure)` (типизированное значение извлекается пока жив VM). Один
  `drain`-путь для монолита и скрипт-систем.
- **Hot-reload.** `Scheduler::remove_system(SystemId)` (ребилд индексов + сброс инкрементального графа;
  id монотонны, не переиспользуются). `ScriptEngine::register_systems` идемпотентен: снимает прошлое
  поколение, регистрирует текущее.
- **Монолитный `run()`** остаётся совместимым fallback (одна эксклюзивная операция вне планировщика).

## Отклонено (реализация `Arc<Mutex<ScriptContext>>` + `Res<ScriptEngine>`), причины

1. **Ложный параллелизм.** Одна `lua_State` однопоточна; `Mutex` вокруг VM держится всё время
   исполнения системы → Lua↔Lua параллелизм нулевой, contention 100% + налог лока. Единственный
   реальный выигрыш (interleaving Lua↔Rust) достижим без Mutex — токеном `ScriptVm`.
2. **Возврат класса дыр F3/ADR-002/S1/S2.** `Res<ScriptEngine>` декларирует «read», а система пишет
   компоненты через VM → недекларированный live-write мимо конфликт-детекции. Декларации обязаны быть
   ДИНАМИЧЕСКИМИ (из запросов скрипта) и видимыми планировщику.
3. **`Arc<Mutex<ScriptContext>>` легализует `world_ptr: NonNull<World>` как `Send+Sync`** — сырой
   указатель на World между потоками, soundness-регресс по построению.
4. **Статические `Query<&mut T>`-сигнатуры не работают для скриптов:** запросы известны только в
   рантайме (строки) и меняются при hot-reload; рукописная Rust-обёртка на каждую Lua-систему убивает
   динамику.
5. **Deadlock вместо громкой паники:** реентрантный `RefCell` — громкая паника, нереентрантный `Mutex` —
   тихий deadlock.
6. **Оценка «100–200 строк» нереалистична:** это архитектурная миграция (реестр скрипт-систем,
   динамические декларации, владение VM), не замена `Rc`→`Arc`.

## Последствия

- Настоящий Lua↔Lua параллелизм — только через **share-nothing VM-пул** (по VM на воркер/группу, общее
  состояние ТОЛЬКО через ECS). Отложено как **фаза C, ⛔ ROI-gated** (условие открытия — профиль реального
  потребителя, показывающий Lua-время значимой долей кадра). До тех пор одна VM + токен `ScriptVm` —
  честная и достаточная модель.
- `Scheduler: !Send` — постоянное свойство (тест 4-поточного пула создаёт+гоняет Scheduler ВНУТРИ
  `install`-замыкания).
- Публичная поверхность: `system{}` (Lua) + `register_systems`/`set_delta_time` (Rust) —
  руководство §17.9. Фундамент масштабируется на agent-IPC (те же динамические декларации).
