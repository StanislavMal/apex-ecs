## 0. TL;DR

Волна 6 закрыла флагманский soundness-🔴 для `Query::new` (алиасящий `&mut` из safe-кода — теперь
ошибка компиляции: `ReadOnlyWorldQuery` + `&mut World`/`new_mut`-конструкторы, B1(в)). Осталась
**вторая половина той же дыры** и две связанные архитектурные цели. Все три едут на ОДНОЙ
инфраструктуре (per-system state-слот), поэтому делаются как единая кампания, а не три правки:

- **В3** — единый `Query<'w,'s>` поверх per-system `QueryState`. Схлопывает query-зоопарк (три типа →
  один, C6) и даёт **дом** для per-system состояния, которое нужно F3 и D8b. Перф — бонус под A/B.
- **F3** — доступ = декларированный SystemParam. Закрывает soundness-дыру: сейчас `SystemContext`
  из safe-кода раздаёт НЕдекларированный мутабельный доступ (`ctx.query::<Write<T>>()`,
  `ctx.resource_mut`, `ctx.event_writer`) → гонка на параллелизме планировщика (тот параллелит по
  ДЕКЛАРИРОВАННОМУ access). Это тот же класс 🔴, что B1(в) закрыл для `Query::new`.
- **D8b** — детерминированное присвоение entity-id при параллельном спавне. §0.9 **превосходство**:
  Bevy этого НЕ гарантирует. Фундамент для replay/rollback-netcode/детерминированных golden-тестов.
  Проектируется так, что **устраняет contention** на общем атомике резерва (быстрее, не медленнее).

**Гейт-принцип волны:** сначала базлайн-бенч (§6), потом реализация; на выходе — ноль регрессий 3-way
и доказанный тестом детерминизм.

## 1. Контекст: что уже есть (факты по коду, HEAD main 26afef7)

- **Borrow-модель B1(в) ✅** (волна 6): `UnsafeWorldCell`, `unsafe trait ReadOnlyWorldQuery`,
  `Query::new`(read-only)/`new_mut`(&mut World)/`unsafe new_unchecked`. `CachedQuery`/`QueryState`
  аналогично. `SubWorld::new`/`with_ranges` + `SystemContext::with_commands` — unsafe. Общий
  `assert_no_self_alias` (C2) гейтит все construction-пути.
- **Query-зоопарк (C6):** три типа с пересекающейся ролью:
  - `Query<'w, Q, F>` (query.rs) — прямой, строит `ArchState` per-arch при конструировании.
  - `CachedQuery<'w, Q>` (world.rs) — заимствует arch-индексы из глобального `QueryCache` ИЛИ из
    `SubWorld` (планировщик предвычислил per-system, zero-alloc).
  - `QueryState<Q>` (world.rs) — персистентный: хранит `ids` + `arch_indices`, инкрементальный
    доскан; **сегодня используется только руками (extract-путь движка), НЕ в plain-fn системах.**
- **Дыра F3 (подтверждено по коду):** `SystemContext::query<Q: WorldQuery>(&self)` — **БЕЗ** бинда
  `ReadOnlyWorldQuery` (в отличие от `World::query`), т.е. `ctx.query::<Write<T>>()` компилируется и
  вызывается без `unsafe`. Плюс `ctx.resource_mut`/`ctx.event_writer`. Планировщик параллелит системы
  по `AccessDescriptor::conflicts_with`, выведенному из ДЕКЛАРИРОВАННЫХ параметров. Система с
  `Res<A>`-декларацией, дёргающая `ctx.resource_mut::<B>()`, и система с `ResMut<B>` — по декларациям
  не конфликтуют → бегут параллельно → пишут B → data race из safe-кода.
  - **Нюанс охвата:** благословенный plain-fn путь (`fn sys(r: Res<A>)`) уже безопасен — пользователь
    `ctx` не видит. Дыра достижима в AutoSystem `run(&self, ctx)` (~16 impl'ов движка) и raw-`par(|ctx|)`.
    Это НЕ «горит», но публичный API; sound-движок не должен иметь safe-достижимую гонку ни в одном пути.
- **Резервация entity-id (факты по entity.rs):** `EntityReserver::reserve()` (`&self`, из параллельных
  систем через `Commands`) → `reserve_from`: `lease.cursor.fetch_sub(1)` (общий снимок free-слотов),
  при исчерпании `high_water.fetch_add(1)` (общий атомик). **Порядок id зависит от порядка атомарных
  операций разных потоков → недетерминирован, И это точка contention.** До flush entity
  «зарезервирована, но не жива» (1:1 Bevy). Аренда free-слотов переарендуется на каждом flush (B2-fix).
- **Command-модель (факты по scheduler):** `thread_commands: Vec<Commands>` — по слоту на rayon-поток;
  `SystemContext::commands()` возвращает `&mut Commands` текущего потока; применяются ПЕР-STAGE (16
  связок `thread_commands`/`current_thread_index`). Commands сейчас per-thread (не per-system) и,
  предположительно, `!Send` (проверить на спайке). D8a уже сделал детерминированный порядок Custom-стадий.

## 2. Workstream В3 — единый `Query<'w,'s>` + per-system state

**Цель.** Один query-тип вместо трёх; per-system state-слот, живущий между вызовами системы, как дом
для (а) `QueryState` (кэш ids + arch-индексов), (б) event-курсоров (F4), (в) командного буфера (D8b).

**Обоснование на планке (НЕ перф).**
- **§0.2b / API-качество:** три типа с пересекающейся ролью — это зоопарк (аудит C6). AAA-эталоны
  (Bevy `Query<'world,'state>`, Flecs) держат ОДИН query-тип. Один тип вместо трёх — читаемость,
  обучаемость, меньше поверхности ошибок.
- **§0.9:** здесь «1:1 Bevy `Query<'w,'s>`» — идиоматически верный Rust (как B1(в)), а не
  mimicry-компенсация. Перенимаем.
- **Структурная необходимость:** F3 (доступ = декларированный параметр) и D8b (per-system буфер) требуют
  per-system state-слота. В3 его вводит. Делать F3/D8b без В3 — плодить ad-hoc хранилища.

**Перф — вторичен, под A/B.** Сегодня plain-fn `fetch(&ctx)` строит `CachedQuery::from_sub_world`:
arch-индексы УЖЕ заимствуются zero-alloc из SubWorld, пересобирается только `fill_ids` (~8 lookup) +
`assert_no_self_alias` (~8). Выигрыш маргинален. **A/B ОБЯЗАТЕЛЕН до внедрения** — класс arch_cols
(реализовано→замерено→отклонено, `[[apex-ecs-benchmark-standing]]`). Рефактор оправдан soundness'ом+API
даже при плоском перфе; но перф не должен регрессировать (§6).

**Подход (эскиз, финализировать на реализации).**
- `SystemParam` получает: `type State: Send + Default` (дефолт `()`), `fn init_state() -> Self::State`,
  `fn get_param<'w>(ctx: &'w SystemContext<'w>, state: &'w mut Self::State) -> Self::Item<'w>`.
  Существующий `fetch(&ctx)` → дефолт поверх `get_param` со stateless `()` (обратная совместимость
  импл-ов, которым state не нужен: Res/ResMut/EventWriter/Commands).
- **Состояние живёт в замыкании `fn_sys`** (замыкание владеет `F::Param::State`), НЕ требуя смены
  хранилища планировщика:
  ```
  let mut state = <F::Param as SystemParam>::init_state();
  Box::new(move |ctx| { if !validate(&ctx) { return } let item = P::get_param(&ctx, &mut state); f.run(item); })
  ```
  (Лайфтайм: state живёт дольше вызова; `&'w mut state` — реборроу на вызов; Item<'w> — ок.)
- Кортежи параметров: `State = (S1, S2, …)`, threading через макро (как уже сделано для `access`/`fetch`).
- Кэшируют только `Query`/`CachedQuery`/`Single`/`QueryParam` (State = кэш ids + резолв-флаг +
  seen_arch_count для инкремента, как нынешний `QueryState`). Остальные — State = `()`.
- **Консолидация типов:** цель — публичный `Query<'w,'s>` как единый вход; `CachedQuery`/`QueryState`
  либо сводятся к нему, либо становятся `pub(crate)` деталью. Точную форму зафиксировать на реализации
  (риск — лайфтаймы 'w/'s в SystemParam::Item; см. Bevy `Query<'world,'state,D,F>`).

**Объём:** 19 impl'ов `SystemParam` + макро кортежей + `fn_sys`-замыкание + консолидация типов. AutoSystem
(`ctx.query`) — не hot-путь, мигрируется вместе с F3.

**Риски:** лайфтаймы 'w/'s (Item заимствует и ctx, и state); взаимодействие с ASD row-split (state
шарится между row-тасками одной системы — должен быть либо read-only на итерации, либо per-task);
change-детекшн тики. **Гейт: Miri TB на новый unsafe + goldens byte-identical.**

## 3. Workstream F3 — доступ = декларированный SystemParam

**Цель.** Убрать из ПУБЛИЧНОГО `SystemContext` возможность недекларированного мутабельного доступа.
Access системы должен быть ПОЛНОСТЬЮ выражен её параметрами — планировщик тогда может доверять
`conflicts_with` (сейчас система может «соврать» про access, дёрнув `ctx.*`).

**Обоснование:** прямая достройка B1(в) до полного soundness (§0.2b). Форма **(a) — золотой путь**
(доступ = параметр), НЕ (b) debug-валидация: (b) — это философия В1(б) (runtime-флаги), от которой мы
сознательно ушли к типам; предлагать её — противоречить траектории.

**Подход.**
- `SystemContext::query<Q>` получает бинд `ReadOnlyWorldQuery` (как `World::query`). Мутабельный
  query — только через декларированный write-параметр (`Query<Write<T>>` в сигнатуре системы), который
  строится планировщиком из SubWorld под провалидированный access.
- `resource_mut`/`event_writer`/`commands` — убрать из публичной поверхности `SystemContext`
  (сделать `pub(crate)`; их зовут только impl'ы `SystemParam` внутри ядра).
- AutoSystem: `run` получает контекст, ограниченный его декларированными associated-типами
  (`type Resources`/`type Events`/`type Query`) — недекларированный доступ становится
  недостижим ПО ТИПАМ. Либо (предпочтительно, если сходится по объёму) — мигрировать AutoSystem'ы
  на plain-fn SystemParam (уже благословенный путь; `add_systems` = единственный вход). Решить на
  реализации по факту объёма (~16 impl'ов + `system!`-макро).
- raw-`par(|ctx|)`: уже несёт `NEEDS_WHOLE_WORLD` — ему честно даётся весь мир; документировать как
  «сырой полный доступ» (осознанный эскейп, не дыра — планировщик не параллелит его с конфликтами).

**Объём:** ~23 движковых `ctx.*`-сайта + внутренние ecs; миграция AutoSystem/`system!`.
**Гейт:** движок собирается (adoption-проход), goldens byte-identical.

## 4. Workstream D8b — детерминизм entity-id (§0.9 превосходство)

**Цель.** Детерминированное присвоение entity-id при параллельном спавне через `Commands`, при
СОХРАНЕНИИ семантики eager `.id()` (код на неё опирается). Это редкая вещь: Bevy детерминизм id под
параллелизмом **не гарантирует** (атомарный reserve). Фундамент replay / rollback-netcode /
детерминированных golden-тестов ядра. Прямое следствие §0.2a: `independent()` УЖЕ продаёт детерминизм —
недетерминированные id делают это обещание частично ложным.

### 4.1 ⚠ ДИЗАЙН-НОТА (load-bearing) — схема детерминированной аллокации id

**Проблема (по коду entity.rs).** `reserve_from` берёт id из ОБЩИХ атомиков (`lease.cursor.fetch_sub`,
`high_water.fetch_add`). Порядок операций разных rayon-потоков → недетерминированный id, И contention
на общем атомике.

**Естественное противоречие.** Плоский `u32`-id, который одновременно (1) **eager** (известен в
параллельной фазе, до flush) и (2) **детерминирован** (= позиция в глобальной последовательности
детерминированного порядка систем) — **невозможен без знания числа спавнов систем меньшего ранга**,
которое в параллельной фазе неизвестно. Нужно ослабить одно из трёх. Развилка:

- **(A) Remap-at-flush:** eager `.id()` = провизорный id, при flush ремапится в детерминированный
  финальный (переиспользуя E6-машинерию MapEntities для ссылок внутри буфера). ❌ Ломает семантику
  «id из `.id()` можно сразу положить в ресурс» (провизорный ≠ финальный после flush; ссылка в ресурсе
  протухнет). Регресс паритета с Bevy (там reserved = final). Отвергнуто как дефолт.
- **(B) Per-system детерминированные id-блоки, eager=final ✅ РЕКОМЕНДАЦИЯ.** Планировщик знает
  ДЕТЕРМИНИРОВАННЫЙ порядок систем стадии (ранг R; D8a уже дал tie-break). В начале стадии каждой
  параллельной системе выдаётся собственный `EntityReserver`, засеянный детерминированной **базой
  блока** (base(R) = Σ размеров блоков рангов < R). Внутри блока система резервирует приватным
  счётчиком (eager, финальный, детерминированный).
  - **Бонус §0.9:** приватный per-system счётчик = **НЕТ cross-thread contention** на общем атомике →
    массовый параллельный спавн становится БЫСТРЕЕ, не медленнее. Детерминизм и перф тянут в одну сторону.
  - **Размер блока:** адаптивный per-system high-water (наблюдённый пик спавнов + slack, напр. 2×).
    Steady-state (после кадра 1) — ноль overflow, полностью детерминирован.
  - **Overflow (редкий путь):** если система исчерпала блок — берёт следующий блок из per-stage
    счётчика **в порядке ранга** (детерминированный медленный путь: короткий lock / rank-ordered
    claim). При адаптивном 2× overflow практически не наступает после прогрева.
  - **free-list/generation:** переиспользование освобождённых слотов тоже должно идти в
    детерминированном порядке (иначе reuse недетерминирован). Аренда free-слотов раздаётся блокам в
    порядке ранга. Проверить на спайке взаимодействие с B2-переарендой.
  - **Порядок команд ВНУТРИ параллельной системы:** `par_for_each` даёт детерминированное МНОЖЕСТВО
    команд, но недетерминированный порядок буфера. С блочной схемой id привязан к порядку резерва
    внутри системы — этот порядок надо сделать детерминированным (резерв по детерминированному ключу
    строки: `(arch_idx, row)` захватывается в момент записи; ASD row-ranges детерминированы).

### 4.2 Граница гарантии (§0.2a — продаём ровно то, что держим)

**Гарантируем: single-binary детерминизм симуляции** — при одинаковом стартовом snapshot + одинаковых
входах один и тот же бинарь воспроизводит идентичное присвоение entity-id, идентичный порядок
применения команд и iteration-independent результат (свободные пишущие системы). Это достаточно для
record/replay и rollback на одной машине/бинаре.

**ЯВНО ВНЕ scope:** битовая FP-идентичность и кросс-платформенный/кросс-компиляторный детерминизм
(отдельная ось: fma/денормали/`fast-math`). НЕ заявляем — иначе §0.2a-полуправда. Документируем границу
в руководстве.

### 4.3 Command-модель

Per-system командные буферы (в per-system state-слоте из В3) вместо `thread_commands[worker]`; apply в
детерминированном порядке систем стадии. Требует: буфер `Send` (или thread-safe сбор) — проверить
статус `Commands: !Send` на спайке; сохранить `size_of::<Command>() ≤ 48`-страж и FIFO.

### 4.4 Шаг 0 — СПАЙК (перед имплементацией D8b)

Прежде чем строить: короткий спайк, доказывающий на стресс-тесте:
1. **Детерминизм:** spawn-тяжёлая параллельная стадия, N прогонов → **идентичное** присвоение id +
   идентичный snapshot (это и есть капстон-тест-гейт).
2. **Ноль перф-регресса (лучше — выигрыш):** микробенч массового параллельного спавна per-system-блоки
   vs текущий общий атомик (ожидаем win из-за отсутствия contention).
3. **Семантика eager `.id()` сохранена:** `.id()`-before-apply возвращает финальный id.

Если блочная схема покажет хрупкость overflow-детерминизма — **фолбэк с УЗКОЙ задокументированной
гарантией:** детерминизм только для последовательного apply + параллельно-спавнящие системы сортируют
записанные команды по захваченному `(arch_idx,row)` перед flush; eager-ссылки внутри буфера ремапятся
(E6), с явной оговоркой про escape id в ресурс. Выбор — по результату спайка, громко в плане.

## 5. Порядок реализации (sequencing)

Зависимости: F3 и D8b едут на per-system state-слоте из В3; D8b-дизайн влияет на форму `Commands`-параметра.

0. **Базлайн-бенч** (§6) — ДО любого кода. Сохранить `wave6b_pre`.
1. **D8b спайк** (§4.4) — валидировать id-схему и перф ПЕРЕД тем, как форма per-system state зацементируется.
   Если фолбэк — зафиксировать сузившуюся гарантию в плане.
2. **В3** — `SystemParam::State`/`get_param`, замыкание `fn_sys`, кортежи, консолидация query-типов.
   Гейт: workspace+clippy+Miri TB+goldens; **A/B vs wave6b_pre — ноль регресса** (перф-заявления — только с числами).
3. **F3** — `ReadOnlyWorldQuery` на `ctx.query`, `pub(crate)` на mutable-аксессоры, миграция
   AutoSystem/`system!`, adoption-проход движка. Гейт: движок собирается, goldens.
4. **D8b** — per-system буферы + детерминированный резерв (блочная схема из спайка) + apply в порядке
   систем. Гейт: **determinism-тест (N прогонов идентичны)** + Miri + goldens + перф.
5. **Финальный 3-way** vs `wave6b_pre` — ноль регрессий во всех 18 группах (шум >5% — расследовать).
6. **Закрытие:** правило ротации (§8) + мерж --no-ff в main обоих репо (локально).

## 7. Тест-план / верификация

- **F3:** тест «система дёргает недекларированный `ctx.resource_mut` → не компилируется / панует громко»
  (компайл-тест trybuild либо runtime-контракт); движок-adoption зелёный.
- **В3:** эквивалентность старому пути (те же результаты итерации/change-детекшн); Miri на state-unsafe;
  инкрементальный доскан архетипов (новый архетип между вызовами системы виден).
- **D8b:** (1) детерминизм — N прогонов идентичны (капстон); (2) eager `.id()`-before-apply = финальный
  id; (3) reuse освобождённых слотов детерминирован; (4) перф массового спавна не хуже (лучше) базлайна;
  (5) взаимодействие с B2-переарендой (нет двойной выдачи).
- Регресс-сьют ядра целиком зелёный; примеры ядра до конца; goldens движка byte-identical на каждом шаге.
